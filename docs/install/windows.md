# Установка на Windows

Установка идёт **внутри WSL2** — это полноценная Ubuntu рядом с Windows, не
эмулятор. Других поддержанных путей нет, и раздел «Почему только WSL2» ниже
объясняет, почему это не перестраховка.

Пошагово, с проверкой после каждого шага. Занимает 30–40 минут, из которых
10–15 — сам мастер. Общая часть, одинаковая для macOS и Windows, — в
[README этой папки](README.md).

## Почему только WSL2

Git Bash выглядит подходящим и в этом главная опасность: bash там
настоящий, `curl` есть, и установка проходит заметную часть пути. Ломается
она позже и по частям.

1. **Профиль разрешений Codex не применяется.** `.codex/config.toml`
   описывает запреты POSIX-путями — `/**/*.env`, `~/.ssh`, запись только в
   `work/`. На Windows-путях это не срабатывает вовсе. Получается ровно
   случай из «Ограничений Codex», пункт 4: агент читает `.env` и ключи,
   сессия при этом выглядит совершенно рабочей, предупреждения нет.
2. **Симлинки превращаются в текстовые файлы.** Их в репозитории
   тринадцать: `AGENTS.md` указывает на `CLAUDE.md`, и все двенадцать
   скиллов в `.claude/skills/` — на `.agents/skills/`. Git для Windows без
   `core.symlinks=true` кладёт вместо них обычные файлы со строчкой пути
   внутри. Codex вместо правил проекта прочитает слово «CLAUDE.md», а ни
   один скилл не найдётся. Тоже молча.
3. **Мелочи, которые видно сразу:** `python3` в MSYS2 называется иначе,
   `~/.config/uzum-ai` уезжает в профиль MSYS.

Общее у всех трёх — установка не падает, а тихо получается неполной.
Поэтому `./setup.sh`, запущенный в Git Bash, останавливается первой же
строкой и отправляет сюда.

Нативная сборка Codex под Windows существует, и её песочница развивается,
но наш профиль разрешений на ней не проверялся ни разу. Сама OpenAI держит
WSL2 рекомендованным способом запускать Codex на Windows: там работает тот
же сандбокс, что на Linux.

## Шаг 0. Что нужно иметь до начала

| Что | Где взять |
|---|---|
| Пароль к ClickHouse WMS | Заявка в JSM, «Доступ к DWH». Логин — корп-почта через дефис |
| Токен Jira | Профиль → Personal Access Tokens → Create token |
| Netbird | Ставится **на Windows**, с правами администратора, см. [ACCESS.md](../../connectors/ACCESS.md) |
| Права администратора | Нужны для `wsl --install` и для Netbird |

Netbird ставится на Windows и остаётся там — внутрь WSL его ставить не
нужно. Как дотянуть до него WSL — шаг 2, и это самое частое место отказа.

## Шаг 1. Поставить WSL2

В **PowerShell от администратора**:

    wsl --install -d Ubuntu

Перезагрузка. При первом запуске Ubuntu попросит придумать логин и пароль —
это отдельная учётка Linux, не пароль Windows. Запомни её: `sudo` внутри
Ubuntu будет спрашивать именно её.

Проверка — в PowerShell:

    wsl -l -v

Должна быть строка `Ubuntu … Running … 2`. Цифра 2 в конце — версия WSL, и
она важна: под WSL1 ничего описанного здесь не работает.

## Шаг 2. Дотянуть WSL до туннеля Netbird

**Читай этот шаг, даже если торопишься.** По умолчанию WSL2 живёт за
собственным NAT со своим сетевым стеком, и маршруты Netbird с Windows туда
не попадают. Прод-данных не будет, а выглядеть это будет как неверный
пароль к ClickHouse — люди на этом теряют по часу.

Лечится зеркальным режимом сети. На стороне **Windows** создай (или
допиши) файл `%UserProfile%\.wslconfig` — обычным блокнотом:

    [wsl2]
    networkingMode=mirrored
    dnsTunneling=true

Затем в PowerShell:

    wsl --shutdown

и открой Ubuntu заново. Нужна **Windows 11 22H2 или новее** — на Windows 10
зеркального режима нет, приходи, разберёмся отдельно.

Netbird при этом должен быть поднят на Windows как обычно.

Проверка появится позже и будет честной: смоук-тест ClickHouse в мастере
ходит на прод-хост живым запросом. Изнутри WSL состояние туннеля снять
нечем, поэтому ни этот документ, ни мастер не станут утверждать, что
всё в порядке, — покажет только реальный запрос.

## Шаг 3. Склонировать репозиторий

Дальше **всё в терминале Ubuntu**, не в PowerShell.

    sudo apt update && sudo apt install -y git
    cd ~
    git clone https://github.com/DayMarket/uzum-data-agent.git
    cd uzum-data-agent

Два важных момента:

- **`cd ~`, а не `/mnt/c/…`.** Домашняя папка WSL — это её собственная
  файловая система. На диске Windows всё работает в разы медленнее, а git
  показывает изменения, которых никто не делал: на этом обрывается
  `git pull --ff-only` в хуке старта сессии, то есть скиллы перестают
  обновляться. `install-windows.sh` на `/mnt/` откажется работать и
  попросит переклонировать.
- **Логины GitHub из Windows в WSL не переезжают.** Репозиторий приватный,
  и внутри Ubuntu нужен свой Personal Access Token — либо
  `sudo apt install gh && gh auth login`.

Переводы строк настраивать не нужно: `.gitattributes` в репозитории
заставляет git отдавать LF на любой машине. Без этого Git для Windows
переписал бы скрипты в CRLF и `./setup.sh` упал бы с `/usr/bin/env: bad
interpreter` — по сообщению не догадаться, при чём тут переводы строк.

## Шаг 4. Установщик окружения

    ./install-windows.sh

Он доводит чистую Ubuntu до состояния, в котором можно работать:

- проверяет, что это действительно WSL и что репозиторий не на диске Windows;
- ставит недостающее — `curl`, `python3`, `uv`, Node.js;
- спрашивает движок (Codex, Claude Code или оба) и ставит его;
- логинит Codex — **до** мастера, а не после: мастер проверяет доверие
  хукам живым запуском `codex exec` и без `~/.codex/auth.json` честно
  откажется, а читается это как «установка сломалась»;
- передаёт управление `./setup.sh`.

Доступов установщик не спрашивает вовсе — это работа мастера, и она здесь
не продублирована.

`sudo` спросит пароль учётки Ubuntu из шага 1, а не пароль Windows.

Аргументы уходят мастеру как есть, так что если `.env` заполнен заранее:

    ./install-windows.sh --non-interactive

## Шаг 5. Мастер

Начинается сам, продолжением предыдущего шага. Что читать в его выводе:

- **«Проверяю окружение…»** — движки, `python3`, `curl`, `uv`, `npx`,
  Netbird. Про Netbird в WSL мастер скажет отдельно: его команды здесь нет
  и не должно быть, вопрос только в зеркальном режиме сети из шага 2.
- **Коннекторы по одному** — вопрос (или подстановка из `.env`) и живая
  проверка. `✓` значит, что сервер реально ответил.
- **Смоук-тест ClickHouse** — вот он и есть настоящая проверка шага 2.
  Не прошёл, а пароль точно верный, — почти наверняка зеркальный режим не
  включился: проверь `.wslconfig` и что после правки был `wsl --shutdown`.
- **Итог** — что включено, что нет и какой командой донести недостающее.
  Самой последней строкой — чего не хватает из **обязательного**; её стоит
  дочитать.

Минимум, чтобы начать работать, — три значения: `CH_WMS_USER`,
`CH_WMS_PASSWORD`, `JIRA_TOKEN`. Остальные семь коннекторов добавляются
потом: `./setup.sh --add <коннектор>`.

## Шаг 6. Команда `uzum` в PATH

Если мастер сказал, что `uzum` не виден, — добавь в `~/.bashrc` и открой
новый терминал:

    export PATH="$HOME/.local/bin:$PATH"

Проверка:

    which uzum

## Шаг 7. Первый запуск

    uzum

У **Codex** будет два экрана подряд: доверие папке, а затем отдельный
«Hooks need review» — там выбирай **«Trust all and continue»**. «Continue
without trusting» оставляет сессию, которая выглядит совершенно обычной,
но хуки в ней молча не запускаются. Ни ошибки, ни предупреждения при этом
не будет — это поведение Codex, а не наш баг.

Перепроверить, что доверие выдано:

    ./setup.sh --add codex-hooks

## Шаг 8. Первая задача

    $task MAD-1234      # Codex
    /task MAD-1234      # Claude Code

Сломалось — `$fix-access` прямо в сессии.

## Если что-то не так

| Симптом | Что это |
|---|---|
| `./setup.sh: /usr/bin/env: bad interpreter` | Скрипт с CRLF. Так бывает, если клон делали Windows-гитом до появления `.gitattributes` — переклонируй изнутри WSL |
| Мастер сразу говорит «это Git Bash, а не Linux» | Ты в Git Bash, а не в Ubuntu. Открой терминал WSL: в меню «Пуск» → Ubuntu |
| Установщик: «репозиторий лежит на диске Windows» | Клон в `/mnt/c/…`. Переклонируй в `~` (шаг 3) |
| ClickHouse не отвечает, пароль точно верный | Шаг 2: зеркальный режим сети. Проверь `.wslconfig`, что после правки был `wsl --shutdown`, и что Netbird поднят на Windows |
| Мастер: «Codex не авторизован» | `codex login`, затем `./setup.sh --add codex-hooks` |
| `bash: uzum: command not found` | Шаг 6 — PATH. Либо запускай как `~/.local/bin/uzum` |
| Коннектора нет в сессии | Скорее всего, так и задумано: без кредов он не включается. Донеси доступ и `./setup.sh --add <коннектор>` |
| Codex спрашивает подтверждение на каждый вызов | Так и есть, см. «Ограничения Codex» в README. Не поломка |
