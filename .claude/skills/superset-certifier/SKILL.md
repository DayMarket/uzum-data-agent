# Superset Dashboard Certifier

## Назначение

Автоматическая проверка дашборда на соответствие:
1. **Правилам публикации** (минимальные требования перед публикацией)
2. **Требованиям сертификации** (3 уровня в зависимости от критичности дашборда)

## Когда использовать

Используй этот скилл, когда просят:
- Проверить, соответствует ли дашборд правилам публикации
- Провалидировать дашборд для сертификации
- Проверить соответствие дашборда корпоративным стандартам
- Подготовить дашборд к подаче на сертификацию

## Общий процесс

```
1. ЧЕЛОВЕК даёт URL дашборда
2. АГЕНТ смотрит свойства и чарты дашборда через коннектор superset
3. АГЕНТ проверяет все требования
4. АГЕНТ формирует отчёт о соответствии со списком проблем
5. АГЕНТ предлагает фиксы
6. ЧЕЛОВЕК подтверждает конкретные фиксы
7. АГЕНТ выполняет только подтверждённые фиксы
```

## КРИТИЧНО: нужно подтверждение человека

**НИКОГДА не применяй фиксы без явного подтверждения!**

После отчёта о соответствии:
1. Покажи полный список найденных проблем
2. Для каждой — опиши, как её починить
3. Спроси, какие фиксы применить
4. Выполняй только то, что подтвердил человек

## Изменения в OpenMetadata

**Для любых изменений в OpenMetadata (OMD) используй коннектор `openmetadata` напрямую.**

Он умеет: искать дашборды/таблицы/метрики, получать полную информацию о сущности,
обновлять сущность (описание, владельцев, теги и т.д.), проверять lineage.
Список инструментов и точные сигнатуры — команда `/mcp`.

**Предпочитай MCP браузеру** для изменений в OMD — быстрее и надёжнее.

# Правила публикации (минимальные требования)

Перед публикацией (Draft → Published) у дашборда ДОЛЖНО быть:

## 1. Соглашение об именовании
- Начинается с префикса бизнес-линии: `Market`, `Ecom`, `Fintech` и т.п.
- Для дашбордов конкретной команды — свой понятный префикс/подпись
- Отражает содержание и назначение
- Хорошие примеры: `Market Ops Main KPI`, `Market: Marketing Overview`

## 2. Роли
- Добавлены роли по умолчанию для команды-владельца
- Если дашборд кросс-командный — создана отдельная гранулярная роль

## 3. Цветовые палитры
Должна использоваться одна из официальных палитр Uzum:
- **Uzum Berry** (рекомендуется, до 18 категорий)
- **Uzum Indigo** (до 12 категорий)
- **Uzum Spectrum** (до 21 категории)
- **Uzum Serenity** (градиент, для смешанных чартов)

## 4. Обязательные теги
У всех дашбордов ДОЛЖНЫ быть теги:
- `cat:` (категория)
- `team:` (команда-владелец)
- `crit:` (критичность: Tier1/Tier2/Tier3/Tier4)

## 5. Лендинг-страница (для важных дашбордов)
Требуется страница в Confluence с кратким описанием.

# Требования сертификации по уровням

## Уровень 1: Стабильность и визуализация

| Требование | Как проверить |
|---|---|
| Все чарты грузятся без ошибок | error rate < 7% за 7 дней на обзорном дашборде Superset |
| Загрузка чарта ≤ 10 сек | время загрузки на обзорном дашборде |
| Чарты работают после применения фильтра | проверить фильтры вручную |
| Все фильтры грузятся корректно | проверить панель фильтров |
| Верно настроен scope фильтра | проверить, что фильтр применяется к нужным чартам |
| Метрики созданы на уровне датасета | проверить конфиг чарта — Metrics vs ad-hoc SQL |
| Есть краткое описание или ссылка на документацию | поле описания дашборда |
| Заданы обязательные теги (cat:, team:, crit:) | теги дашборда |
| Владелец указан в OpenMetadata | каталог OMD |
| Настроены роли доступа | роли дашборда |
| Используется брендовая палитра | цветовая схема дашборда |
| Названия чартов информативны, один язык | заголовки чартов |
| Денежные метрики используют динамический курс | формулы метрик |
| Настроен часовой пояс UTC+5 | настройки данных |

## Уровень 2: Документация и глоссарий (для Tier 1–2)

| Требование | Как проверить |
|---|---|
| Указан домен в OMD | OpenMetadata |
| Указана техническая команда-владелец в OMD | поле Owners |
| Указан Tier в OMD | тег критичности |
| Указан бизнес-владелец | метаданные OMD |
| Есть краткое описание в OMD | поле description |
| Есть ссылка на задачу Jira по разработке | метаданные OMD |
| Указана частота обновления данных | метаданные |
| Указано время обновления (UTC+5) | метаданные |
| Есть ссылки на источники данных и пайплайны | lineage или метаданные |
| Есть ссылка на Confluence (если нужна доп. документация) | метаданные |
| Метрики описаны в разделе Metrics в OMD | каталог метрик |
| Минимум 3 DQ-теста на витрину | dbt-тесты |

## Уровень 3: Высокое качество ETL (для Tier 1)

| Требование | Как проверить |
|---|---|
| Данные строятся через dbt/агрегированные витрины | источники запросов |
| Нет JOIN, критично влияющих на производительность | ревью SQL-запросов |
| Настроены алерты на падение пайплайна | алерты в оркестраторе пайплайнов |

# Уровни критичности

| Tier | Описание | Цель сертификации |
|---|---|---|
| **Tier 1** | Отчётность для C-level, аудит, инвесторы, KPI | Уровень 3 |
| **Tier 2** | Решения среднего менеджмента, KPI департамента | Уровень 2 |
| **Tier 3** | Локальные командные дашборды | Уровень 1 |
| **Tier 4** | Личные, разовые, тестовые | Без сертификации |

# Шаги выполнения

## Шаг 1: получить URL дашборда
```
Человек даёт: https://bi.uzum.uz/superset/dashboard/XXXX/
```

## Шаг 2: открыть дашборд
Логин автоматический (коннектор `superset` сам делает Keycloak SSO). Возьми id или
slug дашборда из URL, который дал человек.

## Шаг 3: прочитать свойства дашборда
```python
mcp__superset__get_dashboard(id_or_slug="<id_or_slug>")   # название, владельцы, описание, published, роли, чарты
```

## Шаг 4: визуальная проверка (опционально)
```python
mcp__superset__get_dashboard_screenshot(dashboard_id=<id>)
```

## Шаг 5: проверить свойства
Из `mcp__superset__get_dashboard` выше проверь:
   - Название (соглашение об именовании)
   - Назначенные роли
   - Цветовую схему
   - Теги (cat:, team:, crit:)

## Шаг 6: проверить чарты
Для каждого чарта:
1. Убедись, что нет ошибки
2. Проверь, что название информативное
3. Проверь использование палитры
4. Проверь, определены ли метрики на уровне датасета

## Шаг 7: проверить внешние источники

### OpenMetadata (OMD)
Через коннектор `openmetadata` найди дашборд по названию и проверь:
- Domain, Owner, Tier, Description
- Частоту обновления данных
- Связанные метрики

### Обзорный дашборд Superset
Открой: `https://bi.uzum.uz/superset/dashboard/superset_overview/`
Примени фильтры:
- Команда: команда-владелец проверяемого дашборда
- Последние 7 дней

Проверь по дашборду/чартам:
- error rate < 7%
- загрузка ≤ 10 сек

## Шаг 8: сформировать отчёт о соответствии

Структура:
```markdown
# Отчёт о сертификации дашборда: [Название]
URL: [dashboard_url]
Дата: [дата]

## Текущий статус
- Требования публикации: [PASS/FAIL]
- Сертификация уровень 1: [PASS/FAIL/N/A]
- Сертификация уровень 2: [PASS/FAIL/N/A]
- Сертификация уровень 3: [PASS/FAIL/N/A]

## Найденные проблемы

### Критичные проблемы (блокируют публикацию)
1. [Описание проблемы]
   - Сейчас: [текущее состояние]
   - Нужно: [ожидаемое состояние]
   - Как починить: [пошагово]

### Проблемы сертификации (уровень 1)
...

### Проблемы сертификации (уровень 2)
...

## Рекомендуемые действия
1. [Действие с оценкой трудоёмкости]
...
```

## Шаг 9: спросить подтверждение

Покажи список фиксов:
```markdown
Нашёл следующие проблемы. Какие фиксы применить?

1. [ ] Добавить недостающий тег `crit:Tier2`
2. [ ] Добавить недостающий тег `team:<команда>`
3. [ ] Обновить название дашборда под соглашение об именовании
4. [ ] Создать страницу в Confluence с описанием
5. [ ] Добавить роли по умолчанию
...

Ответь номерами фиксов (например, «1, 2, 3») или «все»
```

## Шаг 10: выполнить подтверждённые фиксы

### Фикс тегов
```python
# Теги / сертификация живут в json_metadata дашборда. Прочитать, поправить, записать:
mcp__superset__get_dashboard(id_or_slug="<id>")
mcp__superset__update_dashboard(dashboard_id=<id>, json_metadata="<обновлённый json с тегами/сертификацией>")
```

### Создание страницы в Confluence
Страницы с описанием дашборда создаются дочерними к разделу документации по
дашбордам в Confluence (адрес узнай у владельца пространства, если не знаешь).

**ПЕРЕД созданием страницы СПРОСИ у человека:**
```
Для создания страницы описания дашборда нужна информация:

1. Какая частота обновления данных? (например: ежедневно, раз в час, real-time)
2. Во сколько обновляются данные? (UTC+5, например: 08:00)

Пожалуйста, укажи эти данные.
```

Создай страницу через коннектор `atlassian` (Confluence): пространство, родительская
страница, название = название дашборда, содержимое — сгенерированное описание с
частотой обновления.

### Обновление OpenMetadata
**ВАЖНО:** в OMD добавляй ТОЛЬКО краткое описание (не полный текст страницы Confluence).

Описание должно быть кратким саммари, например:
> «Дашборд для анализа производительности склада N: OPH/OPS по сменам и зонам,
> сверка с нормой выработки.»

```python
# Через коннектор openmetadata: обновить описание и домен сущности дашборда
```

**Confluence-страница** содержит все детали (частота обновления, источники данных,
пайплайны, метрики).
**OpenMetadata** содержит только краткое описание + Domain.

```markdown
# ✅ Проверка сертификации завершена

## Дашборд: [Название]

## Сводка
- Найдено проблем: X
- Починено: Y
- Пропущено (не подтверждено): Z

### 1. [Категория изменения]

|---|---|---|

| Теги | `cat:marketing` | `cat:marketing`, `team:marketing`, `crit:Tier2` |
| Роли | (нет) | Market Team Data, Market Viewer |
| Страница Confluence | (нет) | [Создана: ссылка] |

### 2. [Следующее изменение]
| Параметр | Было | Стало |
|---|---|---|
| ... | ... | ... |

## Не починено (человек отказался)
- [Проблема 1]: [причина]

## Осталось (нужны ручные действия)

```

**КРИТИЧНО: для каждого внесённого изменения всегда указывай таблицу было → стало.
Это обязательно для прозрачности и аудита.**
