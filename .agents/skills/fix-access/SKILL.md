# Разбор проблем с доступом

Репозиторий работает в двух движках, и часть проверок у них разная. Сначала
определи, в каком движке ты сам: Claude Code или Codex. Дальше смотри только
свою ветку — чужая даст уверенный неверный диагноз.

1. Посмотри текст ошибки и определи, какой коннектор её дал.
2. Проверь, включён ли он. Файл разный у движков:
   - **Claude Code** — `.claude/settings.local.json`, список
     `enabledMcpjsonServers`.
   - **Codex** — `$CODEX_HOME/uzum.config.toml` (по умолчанию
     `~/.codex/uzum.config.toml`), секции `[mcp_servers.<имя>]`. Это не файл
     репозитория: его кладёт туда `./setup.sh`. В Codex
     `.claude/settings.local.json` не участвует ни в чём — не смотри в него.

   Коннектора нет в нужном файле — подключить: `./setup.sh --add <коннектор>`.

   Коннектора нет и в `secrets.env` нет его переменных — он и не должен быть
   включён: мастер не включает то, для чего нет доступа. Скажи об этом прямо
   и дай команду, а не ищи поломку.
3. **Отличи «процесс запущен» от «инструмент ответил». Это разные вещи, и
   первое ничего не доказывает.**

   `claude mcp list` показывает `✔ Connected` в том числе у коннекторов,
   которые не работают: у `openmetadata`, который падает с кодом 1 ещё до
   рукопожатия, и у `superset`, который падает на первом же вызове (проверено
   живьём на клоне приёмки — там «подключены» были все девять). «Connected»
   означает только, что процесс удалось запустить. У Codex своего списка нет
   вовсе: `codex mcp list` наш профиль не видит.

   **Никогда не пиши человеку «коннектор подключён, значит дело не в нём» на
   основании этого списка.** Единственное доказательство — вызвать самый
   безобидный инструмент этого коннектора на чтение (перечисление:
   `mcp__<коннектор>__list_*`) и посмотреть на ответ:
   - ответил — коннектор жив, причина в другом месте;
   - вернул ошибку — вот она, настоящая причина, разбирай её текст;
   - инструментов коннектора нет в сессии вовсе — он не включён (см. шаг 2)
     или сессию запустили не через `uzum`.
4. Проверь, есть ли переменная в `~/.config/uzum-ai/secrets.env` (значения не
   показывай человеку и не выводи в ответ — только факт наличия).
5. Разбери по типовым причинам:
   - **все прод-источники недоступны** → Netbird не запущен;
   - **коннекторы «ожидают одобрения»** → не принят диалог доверия к папке,
     перезапусти сессию и ответь «да»;
   - **в Codex не видно ни одного коннектора** → сессию запустили голым
     `codex`, а не `uzum`. Профиль подключается флагом `-p uzum`, который
     добавляет только `uzum`; без него нет ни коннекторов, ни запрета читать
     секреты, а сессия выглядит обычной. Выйти и запустить `uzum`;
   - **401 или 403 у Jira, Grafana, OpenMetadata** → истёк токен, перевыпустить
     по инструкции в `connectors/ACCESS.md`;
   - **Superset или Trino просит логин** → истекла SSO-сессия, откроется браузер;
   - **ClickHouse отвергает пароль** → пароль меняется заявкой в JSM. Учётки
     `clickhouse-wms` и `clickhouse-dwh` независимые (два разных кластера) —
     уточни, какой из двух коннекторов жалуется, прежде чем переподключать:
     `./setup.sh --add clickhouse-wms` или `./setup.sh --add clickhouse-dwh`.
6. **Если жалоба про телеметрию** («статистика не собирается», «в отчёте нет
   моих сессий») — посмотри очередь:
   `du -sh ~/.local/state/uzum-ai/queue && ls ~/.local/state/uzum-ai/queue | wc -l`
   Пусто — всё уходит в ClickHouse сразу, дело не в очереди. Файлы копятся —
   база недоступна с этого ноутбука: обычно не поднят Netbird либо телеметрия
   настроена не на тот кластер (таблицы `sandbox.ai_usage_*` живут только на
   складском `wms-clickhouse.prod.um.internal`). Проверить и перенастроить —
   `./setup.sh --add telemetry`; накопленное уедет само при следующем запуске
   сессии. Очередь ограничена по объёму и возрасту, самое старое отбрасывается
   — то есть долгий простой означает потерянные строки, а не разросшийся диск.
7. Дай человеку ровно один следующий шаг, а не список из пяти.
8. Если доступа не хватает совсем — подскажи команду `./setup.sh --add <сервер>`.
